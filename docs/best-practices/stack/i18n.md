# Internationalisation

Applies to `apps/mobile/src/i18n/`. Adapted from the same conventions in `zeki-platform`.

**Catalogues from day one.** The data layer already stores category names per locale
(`transaction_categories.labels`), so the app layer matches it. Retrofitting i18n across 14
screen items later is far more expensive than doing it now.

---

## Stack

Same as `zeki-platform`, so the setup is proven rather than invented:

| Piece | Choice |
|-------|--------|
| Runtime | `i18next` + `react-i18next` |
| Device locale | `expo-localization` → `getLocales()[0]?.languageCode`, mapped to `es` \| `en`, defaulting to `es` |
| Catalogues | `apps/mobile/src/i18n/{es,en}.json` — **flat keys**, `"home.pending_title": "…"`, not nested objects |
| Wiring | `apps/mobile/src/i18n/index.ts` initialises i18next and exports `setLocale()` |
| Enforcement | **`eslint-plugin-i18next`** — see below |

## Enforcement, not just convention

The "no literals in JSX" rule is **machine-enforced**, which is what makes it hold across 14
screen items. In `apps/mobile/eslint.config.mjs`:

```js
{
  files: ['app/**/*.tsx', 'src/**/*.tsx'],
  plugins: { i18next: i18nextPlugin },
  rules: {
    'i18next/no-literal-string': ['error', {
      mode: 'jsx-text-only',
      'jsx-attributes': {
        exclude: ['testID', 'accessibilityLabel', 'accessible'],
      },
    }],
  },
}
```

A literal string in JSX fails `pnpm lint`. Do not add an eslint-disable to get a screen
merged — put the string in the catalogue.

`mode: 'jsx-text-only'` checks JSX **text children** only. A literal in a JSX attribute
(`label="…"`) or inside an object passed through an attribute (`options={{ title: '…' }}`) is
not reported by this mode — the `jsx-attributes.exclude` list above has no effect under
`jsx-text-only` and is kept only so the config does not drift from this rule block. Attribute
copy still needs review; it is not machine-enforced.

Catalogues are flat, dotted-key objects, so i18next must be initialised with
`keySeparator: false` (the default `'.'` separator would otherwise try to walk `home.pending_title`
into a nested `home` object that does not exist, and silently return the key string instead of
the translation).

## Locales and fallbacks

- Supported locales are **`es`** (primary, es-CL) and **`en`** (fallback). Chile is the target
  market; Spanish is the production path.
- Add or update both catalogues in the same change.
- Fallbacks are a safety net, not permission to leave a translation missing.
- The device locale selects the catalogue; anything unresolved falls back to `es`.

## Copy in the app

- **Do not put user-facing literal strings in JSX.** Use `t('…')` with catalogue keys.
- Keys follow a flat namespace matching the screen: `home.pending_title`,
  `categorize.not_sure_label`, `settings_banks.disconnect_confirm`. Every segment — not just the
  leaf — is `snake_case`: `settings_banks.disconnect_confirm`, not `settingsBanks.disconnectConfirm`.
- Keep copy in the namespace of the journey it belongs to, not in a generic bucket.
- **The mockup is the source of the Spanish string.** When copy changes, change
  `design/mockups/mobile/index.html` first, then the `es` catalogue. They must not drift.
- Where a screen has plural, gender, date or number concerns, add a focused test for the
  visible states.

### Plurals

Two shapes exist in the codebase today, both valid — pick whichever the surrounding code already
uses in its screen's namespace, and do not mix them within the same key.

- **Manual branch** (`home.*`, established first): the caller picks between two full keys —
  `category_meta_single` / `category_meta_plural` — with its own `count === 1` check
  (`CategoryBreakdownCard.tsx`). Reads simplest when the compound string has more than one
  interpolated value with different pluralization needs.
- **i18next-native** (`connect_picker.*`, `connect_connected.*`, introduced by item #9): a single
  base key with the CLDR `_one` / `_other` suffix pair — `result_count_one` /
  `result_count_other` — and `t(key, { count })` selects the branch automatically; the base key
  itself (without a suffix) is never a catalogue entry. Reads simplest for one count with one
  wording. `apps/mobile/src/i18n/index.ts` sets no custom `pluralSeparator`, so the default `_`
  applies regardless of `keySeparator: false`.

Converging on one shape across the codebase is a follow-up, not a blocker for either surface.

## Data-driven copy

Some user-facing text comes from the database, not the catalogues:

- `transaction_categories.labels` — resolve by device locale, falling back to `es`. Seeded from
  `design/tokens.json → categoryLabels`, which carries `es` and `en` for all 16 categories.
  That file is the source; do not invent a translation at seed time. `apps/mobile/src/db/labels.ts`
  exports the two pure functions that do the resolving: `toSupportedLocale` (maps a raw
  `languageCode` to `'es' | 'en'`, defaulting to `'es'`) and `resolveLabel` (looks the resolved
  locale up in a row's `labels` and falls back to `es`). `src/db` never reads the device itself —
  it takes an already-resolved `SupportedLocale` as a parameter, so the layering in `AGENTS.md`
  (`app/ → feature hooks → src/db → SQLite`) holds; reading `expo-localization` belongs to
  `src/i18n/`, one layer up.
- `merchants.name` and `financial_institutions.name` — proper nouns, **not translated**.
- `exclusion_reason` and other enum-like values are stored as **stable codes**
  (`personal_transfer`, `not_relevant`). The catalogue resolves them to copy. Never store the
  display string.

The same rule applies to errors: the scraper emits stable `last_error_code` values; the
catalogue turns them into what the user reads in `bank-review/error`. Never persist a
translated message.

## Formatting

Currency, dates and numbers are **not** catalogue strings. They go through
`@finanzas/shared-utils`, which is unit-tested.

**Formatters take the active locale as a parameter and use `Intl`.** Do not hand-write a
Spanish month table — `Intl.DateTimeFormat` already knows both languages, and hardcoding one
leaves Spanish dates under an English UI:

```ts
new Intl.DateTimeFormat(locale, { day: 'numeric', month: 'short' }).format(d)  // "24 ene"
```

Two caveats, both to verify in the implementation plan rather than assume:

- **Hermes needs full ICU** for non-English `Intl` output. If the build does not have it, ship
  an `es` table behind the same locale-parameterised signature and record it as a known
  limitation — never change the signature.
- `Intl.NumberFormat` for CLP must be checked against the mockups: the format is `$1.200.000`,
  point as thousands separator, no decimals. If the platform output differs, format by hand —
  the mockup wins, not the platform default.

## Testing

- Test locale fallback behaviour when touching the resolver.
- Screen tests assert behaviour and key-driven output; do not duplicate every translation
  string in assertions.
- **Visual checks use Spanish**, because it is both the longest text and the real production
  path. A layout that only survives English is broken.
