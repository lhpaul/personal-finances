## Summary

**Approach**: Add the app's entire persistence layer under `apps/mobile/src/db/`, declared once
in `schema.ts` with `drizzle-orm/sqlite-core` so the same declaration drives both the on-device
`expo-sqlite` runtime and an in-memory `better-sqlite3` store used by the whole test suite. The
inclusion rule lives in exactly one file (`fragments.ts`) and a source scanner test fails the
build if any other file restates it. Migrations are generated by `drizzle-kit`
(`dialect: 'sqlite'`, `driver: 'expo'`) and are proven safe by a custom `db:check` CLI that runs
four modes: drizzle-kit's own journal-integrity check, a "history applies to an empty store and
matches the declared shape with no pending difference" mode, a pairwise snapshot analyser that
mechanically rejects non-additive changes, and a preservation mode that replays the pending
change set against every committed store snapshot and asserts nothing is lost or altered.
Starter content is applied through a new `seed_ledger` table that remembers what was last written
per stable seed key, which is what lets a refresh insert genuinely new starter records, correct
records the person never touched, and never overwrite an edit or resurrect a deletion.

**Estimated complexity**: L

**Rationale**: Twelve tables with their full constraint and index surface, a migration runner, a
four-mode verification CLI with its own analysers and unit tests, an idempotent upsert that must
be proven not to overwrite nine person-owned columns, a ledger-driven seeder with three distinct
refresh behaviours, and a transactional category-deletion cascade. The individual pieces are not
algorithmically hard, but the item ships two pieces of bespoke tooling (the additivity analyser
and the inclusion-rule scanner) that each need their own edge-case test suite, and every one of
the 29 acceptance criteria has to be demonstrable without a device.

**Dependencies**: Item #1 (bootstrap the monorepo and the Expo app) — **merged**; `apps/mobile`,
its Jest wiring and the CI workflow all exist. No other item blocks this one. Item #4
(`@finanzas/shared-utils` money/date/RUT helpers) is running concurrently and is **not** a
dependency: this item deliberately writes no money or date helper (see Risks).

## Key Decisions

Each decision below is referenced by index from the Layer-by-Layer, Testing and Implementation
Order sections. Indices are stable within this document.

**Decision 1 — one schema declaration, two drivers.** `src/db/schema.ts` imports only from
`drizzle-orm/sqlite-core`, which is platform-free. The on-device client
(`src/db/client.ts`) is the **only** file in the repository that imports `expo-sqlite`, and it
wraps it with `drizzle-orm/expo-sqlite`. The test client (`src/db/testing/memory-db.ts`) opens
`better-sqlite3` at `':memory:'` and wraps it with `drizzle-orm/better-sqlite3`. Both driver
classes extend `BaseSQLiteDatabase<'sync', …>` (Verification Log), so repository functions are
written once against that base type and run unchanged in both environments. This is the mechanism
behind AC24: the entire suite runs in Node, with no simulator and no device.

**Decision 2 — `better-sqlite3` is the Node-side driver, with a named fallback.** It is the
driver Drizzle documents for Node, it is synchronous (matching the `'sync'` database type the
Expo driver also uses, so no test/runtime behavioural skew), and it is a full SQLite build with
partial-index, expression-index, trigger and `PRAGMA` support — all of which this schema needs.
It is a `devDependency` of `@finanzas/mobile` only, is never imported from `app/` or from any
non-test file under `src/`, and is therefore never seen by Metro.
*Unverified against this repository (no native dependency is installed yet)*: that the
`better-sqlite3` prebuilt binary loads under Node 22 on both the developer machine and
`ubuntu-latest`. If it does not, fall back to `@libsql/client` +
`drizzle-orm/libsql` (`:memory:`), which is the other in-memory SQLite driver Drizzle ships;
do **not** fall back to mocking SQLite, because every constraint assertion in this item depends
on a real engine.

**Decision 3 — `apps/mobile/jest.config.js` becomes a two-project config.** Project `app` keeps
`preset: 'jest-expo'` and ignores `src/db/`; project `db` uses `testEnvironment: 'node'` with
`babel-jest` + `babel-preset-expo` and matches only `src/db/**/*.test.ts`. Rationale: the
`jest-expo` preset installs React Native module mocks and a React Native-flavoured environment
that a native Node addon and a Node-only test tier do not need and can be destabilised by.
`pnpm --filter @finanzas/mobile test` runs both projects, so AC24's "runs as part of the
repository's existing test command" holds with no new command.

**Decision 4 — money never touches a `real` column, and that is asserted mechanically.** No
column in `schema.ts` uses `real()`. `src/db/money.ts` exports
`assertMinorUnits(value: number, field: string): number`, which throws unless
`Number.isInteger(value)`; every write path that carries money (`transactions.amount`,
`transactions.included_amount`, `user_budgets.amount`,
`user_recurring_transactions.amount`, and the money keys inside
`user_financial_products.metadata`) goes through it. Two tests back this: one walks
`PRAGMA table_info` for every table of the migrated store and fails on any declared type matching
`/real|float|double|numeric/i`; the other feeds a fractional balance into the product-metadata
guard and asserts rejection (AC4).

**Decision 5 — `PRAGMA foreign_keys = ON` is set on every connection, in both environments.**
SQLite disables foreign-key enforcement by default. Without this pragma every
`ON DELETE CASCADE` in [`docs/project/4-database-model.md`](../../../project/4-database-model.md)
is decorative, and the deletion guarantees of AC22 would pass in review and fail on a device.
Both `src/db/client.ts` and `src/db/testing/memory-db.ts` issue it immediately after opening,
and a test asserts `PRAGMA foreign_keys` reads back `1` on the test client.

**Decision 6 — `db:check` is a custom CLI, because `drizzle-kit` cannot be one.** `drizzle-kit`
rejects `migrate`, `studio` and `pull` under `driver: 'expo'` (Verification Log), and its own
`check` command only validates journal integrity. `db:check` is therefore
`apps/mobile/scripts/db/check.ts`, run with `tsx`, executing four modes in order and failing on
the first failure:

| Mode | What it does | Satisfies |
| --- | --- | --- |
| 0 — journal integrity | Shells out to `drizzle-kit check --config drizzle.config.ts`. Catches snapshot-version drift, malformed snapshots and parent-id collisions from a bad merge | Use Case 5 |
| 1 — history vs declared shape | Opens an empty in-memory store, runs the full migration history, introspects it (`sqlite_master`, `PRAGMA table_info`, `PRAGMA index_list`, `PRAGMA index_info`, `PRAGMA foreign_key_list`) and compares against the newest `drizzle/meta/*_snapshot.json`. Then copies `drizzle/` to a temp directory, runs `drizzle-kit generate` against it, and fails if a new `.sql` migration is emitted | AC12 |
| 2 — additive-only | Runs the analyser of Decision 7 over every consecutive snapshot pair in `drizzle/meta/` | AC14 |
| 3 — preservation | For every committed store snapshot in `src/db/__fixtures__/store-v*.sql`: load it into an in-memory store, take a full census, run the migration history, re-census, and assert no table, no row and no pre-existing column value changed | AC13 |

Mode 1's second half is what makes "no pending difference" mechanical rather than a promise: if
`schema.ts` and the migration history disagree in any way Drizzle can see, Drizzle itself emits
the difference as SQL and the check fails printing it.

**Decision 7 — additivity is enforced by a pairwise snapshot analyser, not by review.**
`src/db/checks/additivity.ts` exports
`findNonAdditiveChanges(prev: SqliteSnapshot, next: SqliteSnapshot): Finding[]`. It is a pure
function over two parsed `drizzle/meta/*_snapshot.json` objects — no file system, no database —
so it is unit-testable in milliseconds. A `Finding` is
`{ kind, table, column?, detail }` and every kind is a hard failure that names what would be
lost:

| `kind` | Condition | Why it is fatal in the field |
| --- | --- | --- |
| `table_removed` | A table in `prev.tables` is absent from `next.tables` | Every row of it is gone. Also how a table rename appears |
| `column_removed` | A column in `prev` is absent from `next` for a table present in both | Every value in it is gone. Also how a column rename appears |
| `column_type_changed` | `prev.type` differs from `next.type` (case-insensitively) | SQLite rebuilds the table and coerces every value |
| `column_made_mandatory` | `notNull` goes `false` → `true` | Fails on the first existing row holding `NULL` |
| `column_pk_changed` | `primaryKey` differs | Table rebuild |
| `new_mandatory_column` | A column added to a **pre-existing** table with `notNull: true` and no `default` | `ALTER TABLE ADD COLUMN NOT NULL` without a default is rejected outright by SQLite when rows exist |
| `new_unique_on_existing_table` | A `uniqueConstraints` entry or an index with `isUnique: true` added to a pre-existing table | Tightening a constraint on data already on the phone; throws on the first duplicate |
| `check_added_or_changed_on_existing_table` | A `checkConstraint` added to or changed on a pre-existing table | Same class: a constraint tightened over existing rows |
| `fk_added_to_existing_table` | A `foreignKeys` entry added to a pre-existing table | SQLite has no `ADD CONSTRAINT`; drizzle-kit emits a copy-and-rename table rebuild, which is exactly the unrecoverable pattern |
| `default_removed_from_mandatory_column` | A `notNull` column loses its `default` | Turns a later `ADD COLUMN` recipe into a rejected one |

Explicitly **allowed**, and asserted as allowed by unit tests: a new table (with any constraints,
because it has no existing rows), a new nullable column on an existing table, a new `notNull`
column **with** a default on an existing table, a new non-unique index, and the removal of a
non-unique index.

**Decision 8 — there is no suppression directive for a non-additive finding, by design.** The
recovery path for a rejected change is the one
[`docs/best-practices/stack/sqlite-drizzle.md`](../../../best-practices/stack/sqlite-drizzle.md)
already prescribes: to "remove" a column, stop writing it and leave it; to "rename" one, add the
new column, backfill, write both for a release, then stop reading the old. A suppression comment
would let a contributor ship the one class of change that cannot be repaired on a user's phone.
The analyser recognises no directives, and the scanner of Decision 9 recognises none either.

**Decision 9 — the inclusion rule is one file, and a scanner proves it.**
`src/db/fragments.ts` exports exactly two values:

```ts
// Illustrative — adapt during implementation
export const isIncluded = sql`${transactions.excludedAt} is null`;
export const includedAmount = sql`coalesce(${transactions.includedAmount}, ${transactions.amount})`;
```

`src/db/checks/inclusion-rule-scan.ts` exports a pure
`findInclusionRuleRestatements(source: string, filePath: string): Finding[]`, and
`src/db/__tests__/inclusion-rule-single-definition.test.ts` runs it over every `.ts`/`.tsx` file
under `apps/mobile/src/` and `apps/mobile/app/`, allowlisting only `src/db/fragments.ts` (the
definition) and `src/db/schema.ts` (the column declaration). This is the enforcement mechanism
behind AC20 and Business Rule 6; the scanner's edge cases and unit tests are enumerated in the
Testing Strategy's parser-risk addendum.

**Decision 10 — starter content is driven by a `seed_ledger` table.** `user_id IS NULL` cannot
distinguish "never seeded on this device" from "starter row the person deleted", which is exactly
what spec Decision 2 flags as needing provisioning now. `seed_ledger` records, per stable seed
key, which row the seeder created and a digest of the values it last wrote:

| Column | Type | Notes |
| --- | --- | --- |
| `seed_key` | `TEXT PK` | `financial_institution:banco-de-chile`, `transaction_category:comida`, `merchant:lider`, `merchant_alias:lider:LIDER` |
| `entity_type` | `TEXT NOT NULL` | `financial_institution` \| `transaction_category` \| `merchant` \| `merchant_alias` |
| `entity_id` | `TEXT NOT NULL` | The primary key of the row this seed created |
| `seeded_hash` | `TEXT NOT NULL` | Digest of the seed-owned field values as last written |
| `created_at` | `TEXT NOT NULL` | |
| `updated_at` | `TEXT NOT NULL` | |

The whole seed run is one transaction (Business Rule 16, AC19). Per seed record:

1. **No ledger row** → never applied on this device → insert the entity row and the ledger row.
   This is both the fresh-install path (AC1, AC2) and the "a later app version added a starter
   record" path (AC18).
2. **Ledger row exists, entity row missing** → the person deleted it → **do nothing**. The ledger
   row stays, so no later run resurrects it (Business Rule 15, AC17).
3. **Ledger row exists, entity row present, current seed-owned values hash equal to
   `seeded_hash`** → untouched by the person → update it to the current catalogue values and
   refresh `seeded_hash`. This is what lets a corrected `categoryLabels.en` reach existing users,
   which the spec's Categories section explicitly requires.
4. **Ledger row exists, entity row present, hash differs** → the person edited it → **do
   nothing**, and do not refresh `seeded_hash` (Business Rule 15, AC17).

Rows the person created are never read by the seeder at all, because it only ever touches ids it
finds in its own ledger (Business Rule 14). `user_id` is never written by a seed. The direction
column `income` is deliberately **excluded from the update statement** in case 3, so no catalogue
change can ever flip an existing category's direction (AC29).

**Decision 11 — seeded rows get deterministic primary keys.** A seeded row's `id` is its stable
identifier: `financial_institutions.id` is the institution slug (already normative in the data
model, and `banco-de-chile` must match the scraper's `bankId`);
`transaction_categories.id` is the category slug; `merchants.id` is the merchant slug;
`merchant_aliases.id` is `<merchant-slug>:<normalised-pattern>`. Person-created rows get a
generated UUID. Rationale: the committed store snapshot (`store-v1.sql`) is a text file that
reviewers read and that the secrets test greps, so its primary keys must be stable across
regeneration; a random id would make every `db:seed` produce a spurious diff.

**Decision 12 — `src/db` takes a resolved locale; it never reads the device.** Repository
functions that return a category name accept `locale: SupportedLocale` (`'es' | 'en'`), so
`src/db` stays free of platform concerns and the layering in `AGENTS.md`
(`app/ → feature hooks → src/db → SQLite`) holds. `src/db/labels.ts` exports two pure functions:
`toSupportedLocale(languageCode: string | null | undefined): SupportedLocale`, which lower-cases,
takes the part before any `-`, returns `'en'` for `en`, and returns `'es'` for everything else
including `null`/`undefined`; and `resolveLabel(labels: CategoryLabels, locale): string`, which
looks the locale up directly in `labels` and falls back to `es`. That is the two-tier resolver
spec Decision 4 mandates. It deliberately does **not** import `expo-localization`: the
`getLocales()[0]?.languageCode` read belongs to `src/i18n/`, which is item #2's surface and must
not be touched here. See Risks for the reconciliation follow-up.

**Decision 13 — hashing and id generation are injected ports, not imports.** `expo-crypto` is a
native module; the test tier must not load it. `src/db/dedup.ts` exports the pure
`buildDedupInput(row): string`; repositories take a `DbPorts` object
`{ digestSha256(input: string): Promise<string>; newId(): string; now(): string }`. The runtime
supplies `expo-crypto`'s `digestStringAsync` and `randomUUID`; tests supply `node:crypto` and a
deterministic counter, which is also what makes the committed fixture reproducible.

**Decision 14 — the dedup input includes `external_id`, and the row id for manual entries.**
[`docs/project/4-database-model.md`](../../../project/4-database-model.md) states
`dedup_hash = sha256(user_financial_product_id, date_local, amount, raw_description)` **and**
`UNIQUE(dedup_hash)`. Those two together reject a second genuinely-distinct movement that happens
to share a product, day, amount and description — two identical coffees on the same day, each
with its own bank identifier. The declared input becomes

```text
[user_financial_product_id, date_local, String(amount), raw_description, external_id ?? '', is_manual ? id : ''].join('␟')
```

For a bank that supplies no identifier and for a non-manual row this reduces exactly to the
documented formula, so the fallback route's meaning is unchanged; for a bank that does supply
one, identity is the identifier and the fingerprint stops colliding. This is an **intentional
difference from the data model** and AC28 requires it to be reflected in
`docs/project/4-database-model.md` in the same change — it is listed in Documentation Updates.

**Decision 15 — the upsert is lookup-then-write inside one transaction, not
`onConflictDoUpdate`.** SQLite's `ON CONFLICT` takes a single conflict target, and this item has
two identity routes (`(user_financial_product_id, external_id)` when the bank supplies an
identifier, `dedup_hash` when it does not). `upsertBankTransactions` therefore, per row and
inside one transaction: selects by external id when one is present, otherwise by `dedup_hash`;
on a hit, updates **only** the bank-owned columns `amount`, `type`, `currency_code`,
`occurred_at`, `date_local`, `raw_description`, `metadata`, `dedup_hash`, `updated_at`; on a
miss, inserts. The nine person-owned columns — `transaction_category_id`, `category_source`,
`note`, `review_flag`, `excluded_at`, `exclusion_reason`, `exclusion_note`, `included_amount`,
`merchant_id` — plus `is_manual` never appear in the update statement's `set` object. The unique
indexes remain the store-level backstop required by AC21: a test issues a raw duplicate insert
that bypasses the repository and asserts the store rejects it.

**Decision 16 — the two ✨ Otros categories are protected by a database trigger.** The repository
`deleteCategory` refuses them by slug, and a `BEFORE DELETE` trigger created in the first
migration raises `ABORT` for `slug IN ('otros-gasto','otros-ingreso')`, so a raw delete that
bypasses the repository is also rejected (AC9). The trigger is appended by hand to the generated
`0000_*.sql` migration file. drizzle-kit's differ only tracks tables, columns, indexes, views and
constraints, so an appended trigger does not appear as a "pending difference" in `db:check` mode
1 — mode 1's live-vs-snapshot comparison deliberately compares tables, columns, indexes and
foreign keys, and ignores triggers. Implementation Order Step 5 is the first run of `db:check`
and verifies this, immediately after the trigger has been appended in Step 4.

**Decision 17 — `schema_version` is the count of applied journal entries.** After `migrate()`
returns, the bootstrap writes `app_settings.schema_version` = the number of entries in
`drizzle/meta/_journal.json` that have been applied, which is `1` for this first release. It is
written **after** a successful migrate and never before (Business Rule 11). Because Drizzle wraps
the whole batch in one transaction and rolls it back on failure (Verification Log), a failed
migration leaves both the store and `schema_version` at the last fully applied version with no
extra work; if the process dies between `migrate()` and the `schema_version` write, the next
launch's migrate is a no-op and the value is re-derived and re-written, so the sequence is
idempotent (AC15, AC16).

**Decision 18 — a store snapshot is committed as deterministic SQL text, not as a binary
`.db`.** `src/db/__fixtures__/store-v1.sql` is produced by `pnpm --filter @finanzas/mobile
db:seed`, which builds a store at the current version containing all starter content plus a
representative set of person-owned data, then dumps it with a deterministic dumper (tables sorted
by name, rows sorted by primary key, one `INSERT` per row, `__drizzle_migrations` included).
Rationale: a text snapshot is diffable in review, greppable by the credential-scan test that
AC5 requires over "every committed snapshot", and free of the binary-blob-in-git problem. `db:check`
mode 3 loads it by executing the file against an empty in-memory store.

**Decision 19 — the SQL access boundary is enforced by lint and by a test.** Item #1's root
`eslint.config.mjs` already named-exports `sharedDomainPurity`; this item adds a second named
export `dbAccessBoundary` — a `no-restricted-imports` block forbidding `drizzle-orm`,
`drizzle-orm/*`, `expo-sqlite` and `better-sqlite3` — applied from
`apps/mobile/eslint.config.mjs` to `app/**` and `src/**` with `src/db/**` ignored. A companion
test (`src/db/__tests__/db-access-boundary.test.ts`) scans the same tree for those import
specifiers, so the guarantee survives a lint-config regression (AC26).

**Decision 20 — no network, no analytics, no export.** This item adds exactly eight dependencies:
`expo-sqlite`, `expo-crypto` and `drizzle-orm` at runtime; `drizzle-kit`, `better-sqlite3`,
`@types/better-sqlite3`, `tsx` and `babel-plugin-inline-import` as devDependencies. None of them
opens a socket. There is no fetch, no upload, no crash reporter and no telemetry anywhere in this
item (AC27, Business Rule 24), and Implementation Order Step 12 includes an explicit diff review
for it.

**Test types**: Unit (Jest, Node tier, in-memory SQLite) + a command-line verification runbook.

**Key scenarios to test**:

1. Fresh bootstrap on an empty store creates every table and applies all starter content, with no
   error and no set-up step (AC1).
2. After bootstrap: six institutions with exactly one `available` (`banco-de-chile`); sixteen
   categories with the exact slug set of the Seed Data Contract; every starter merchant has at

### Parser-risk addendum

Classified **parser-risk**. Two of this item's deliverables are scanners over structured text:
`src/db/checks/inclusion-rule-scan.ts` applies regular expressions to TypeScript source, and
`src/db/checks/additivity.ts` walks structured JSON snapshots. Both gate acceptance criteria
(AC20 and AC14), so a silent scanning bug would silently disable the guarantee.

#### Edge-case enumeration — `findInclusionRuleRestatements`

Contract: `findInclusionRuleRestatements(source: string, filePath: string): Finding[]`. It strips
line and block comments, extracts every `` sql`…` `` tagged-template body (including the contents
of its `${…}` interpolations, and including nested `sql` tags), and applies three rules — **A**:
a `sql` template body mentioning `excluded`, `included_amount` or `includedAmount`; **B**:
`isNull(` or `isNotNull(` applied to any expression ending in `.excludedAt`; **C**: the snake_case
literals `excluded_at` or `included_amount` anywhere in the file. `src/db/fragments.ts` and
`src/db/schema.ts` are allowlisted by `filePath`.

| Input | Expected | Why it matters |
| --- | --- | --- |
| `` where(sql`${transactions.excludedAt} is null`) `` in a repository | 1 finding, rule A | The canonical second definition — the exact failure the guard exists for |
| `sql.raw('excluded_at IS NULL')` | 1 finding, rule C | The raw-string form evades rule A entirely |
| `isNull(transactions.excludedAt)` | 1 finding, rule B | The Drizzle-operator form contains no SQL text at all |
| `isNull(t.excludedAt)` with `const t = transactions` | 1 finding, rule B | An alias must not evade rule B |
| `isNotNull(transactions.excludedAt)` | 1 finding, rule B | Boundary variant: the negated operator |
| `` sql`${t.excludedAt} is null and coalesce(${t.includedAmount}, ${t.amount}) > 0` `` | 2 findings on one line | Multiple occurrences on a single line must each be reported |
| `` sql`select 1 from x where a in (${sql`${t.excludedAt} is null`})` `` | 1 finding from the inner body | Nested tagged templates: the inner construct must still be scanned |
| `where(isIncluded)` / `sum(includedAmount)` | 0 findings | The correct use of the fragment must never be flagged |
| `.set({ excludedAt: nowIso, exclusionReason: 'other' })` | 0 findings | Writing the value is not restating the rule |
| `if (row.excludedAt !== null) { … }` | 0 findings | Reading the value in JavaScript is not restating the rule |
| `// excluded_at is null — see fragments.ts` | 0 findings | Comments are stripped before scanning, so documentation is allowed |
| `/* excluded_at is null */` spanning two lines | 0 findings | Block comments too, including multi-line ones |
| `` `plain template ${transactions.excludedAt}` `` (untagged) | 0 findings | Negative lookalike: an untagged template is not SQL |
| `` mysql`${t.excludedAt} is null` `` and `` sqlish`…` `` | 0 findings | Negative lookalike: only the exact tag `sql` counts, matched with a non-word-character boundary |
| `import { isIncluded } from '../fragments';` | 0 findings | Negative case: an import specifier must not trip rule C |
| Source using CRLF line endings | Identical findings to the LF form | Boundary-character variant: line-ending normalisation must not change the result |
| `filePath` = `src/db/fragments.ts` containing all three forms | 0 findings | The allowlist is the definition itself |
| `filePath` = `src/db/schema.ts` containing `integer('included_amount')` | 0 findings | The allowlist is the column declaration |

#### Edge-case enumeration — `findNonAdditiveChanges`

| Input (`prev` → `next`) | Expected | Why it matters |
| --- | --- | --- |
| Table `merchants` present → absent | `table_removed` | Every merchant row lost |
| `transactions.note` present → absent | `column_removed` | Every note lost |
| `transactions.note` renamed to `user_note` | `column_removed` **and** no `new_mandatory_column` | A rename is only ever visible as a removal plus an addition |
| `transactions.amount` `integer` → `real` | `column_type_changed` | Coercion of every stored amount |
| `transactions.amount` `INTEGER` → `integer` | 0 findings | Boundary variant: type comparison is case-insensitive, so a serializer casing change is not a false alarm |
| `transactions.note` `notNull` `false` → `true` | `column_made_mandatory` | Fails on the first row holding `NULL` |
| New column `transactions.foo` with `notNull: true`, no default, on the existing table | `new_mandatory_column` | SQLite rejects the `ALTER TABLE` outright |
| New column `transactions.foo` with `notNull: true` **and** a default | 0 findings | The one mandatory addition that is safe |
| New column `transactions.foo`, nullable | 0 findings | The canonical additive change |
| Brand-new table with `notNull` columns, uniques, checks and foreign keys | 0 findings | A new table has no existing rows, so nothing can be tightened |
| New unique index on the existing `transactions` table | `new_unique_on_existing_table` | Throws on the first duplicate already on the phone |
| New **non-unique** index on `transactions` | 0 findings | Explicitly allowed |
| Existing non-unique index removed | 0 findings | No data loss |
| `checkConstraint` added to the existing `merchants` table | `check_added_or_changed_on_existing_table` | A constraint tightened over existing rows |
| `foreignKeys` entry added to the existing `transactions` table | `fk_added_to_existing_table` | drizzle-kit emits a copy-and-rename table rebuild |
| `notNull` column loses its `default` | `default_removed_from_mandatory_column` | Turns a later safe `ADD COLUMN` into a rejected one |
| Two independent violations in one pair | 2 findings, each naming its own table and column | Multiple findings must not collapse into the first |
| `prev` and `next` identical | 0 findings | The no-op case, which mode 3 relies on |

  (18 cases), each asserting the exact finding count and rule.
- `src/db/checks/__tests__/additivity.test.ts` — one `it(...)` per row of the second table

#### Suppression semantics

**No suppression directive is recognised, in either scanner, by design (Decision 8).** There is no
comment, pragma or allowlist file that lets a contributor ship a second inclusion rule or a
non-additive migration. The only allowlist is the two-file path allowlist inside the
inclusion-rule scanner (`src/db/fragments.ts` and `src/db/schema.ts`), which is hard-coded in the
scanner rather than read from source, so a source file cannot add itself to it. If a genuinely new
file ever needs to be allowlisted, that is a code change to the scanner and a reviewer decision,
not an inline directive.

### Concurrent-event-source addendum

Classified **applicable, narrowly**: `ensureDatabaseReady()` is an initialisation sequence that
can race with the app code that queries the store, and it can be called from more than one React
component mounting at once. There are no sockets, listeners or timers in this item.

- **Shared mutable state guards**: the only shared mutable state is the module-level
  `bootstrapPromise` in `src/db/bootstrap.ts` and the SQLite connection itself. The promise is
  written exactly once, on the first call, before any `await`, so there is no interleaving window.
  SQLite serialises writes internally, and every multi-statement write in this item runs inside an
  explicit transaction.
- **Re-entrancy / in-flight tracking**: yes, a second caller can arrive before the first finishes.
  Handled by single-flight: `ensureDatabaseReady()` returns the existing `bootstrapPromise` when
  one exists, so migrations and seeds run at most once per process. A test calls it three times
  concurrently and asserts the seed row count is the fresh-install count, not a multiple of it.
- **Event deduplication**: the only repeatable "event" is a repeated bootstrap after a failure.
  Every step is idempotent (migrate skips applied entries; `schema_version` is an upsert;
  `first_launch_at` is written only when absent; the seed ledger makes each seed key
  apply-once-per-state). On failure the promise is cleared so the next launch genuinely retries.
- **Listener and resource cleanup**: not applicable — no listeners or timers are registered. The
  SQLite connection lives for the process lifetime; the test client is closed in `afterEach`.
- **Race conditions at initialisation**: a query issued before the store is ready would hit a
  missing table. Prevented by the layering contract: every repository function takes the database
  handle that `ensureDatabaseReady()` resolves to, so a caller cannot obtain a handle before
  bootstrap has completed. This item exports no module-level pre-opened handle.
- **Race conditions at teardown**: not applicable in this item. There is no teardown path; the
  development-only "Reset local database" action named in the spec's Operational Visibility is
  owned by the settings item.
- **Error propagation across async boundaries**: `ensureDatabaseReady()` rejects with a typed
  `DatabaseBootstrapError` (`cause` = the underlying `DatabaseMigrationError` or seed error).
  Nothing is swallowed, nothing is logged-and-ignored, and the rejected promise is not cached as
  a permanent failure — it is cleared so a retry is possible (AC16).
- **New concurrent patterns**: single-flight initialisation is new to this codebase (item #1
  introduced no async state at all). It is the simplest pattern that satisfies "preparation is
  all-or-nothing" without a lock library.

### Residual verification strategy

This item is both a pattern-completeness item ("every table and field in the data model", "the
sixteen starter categories") and a guarantee item ("the inclusion rule exists once", "migrations
are additive"). Before requesting `ready-for-human-review`, the implementation pull request
description must record:

- **Evidence source for schema completeness**: the passing table-and-column census test (scenario
  28), which asserts an explicit expected set rather than a count — a count can match while a
  column name or nullability differs. Plus a stated side-by-side read of `schema.ts` against
  `docs/project/4-database-model.md` (Step 3).
- **Evidence source for seed completeness**: the passing seed tests (scenarios 2, 3, 29), whose
  expected slug set is derived from `design/tokens.json` at test time, so a token edit cannot
  leave the assertion stale.
- **Evidence source for the additive-only guarantee**: the Step 11 negative control output —
  `db:check` failing with `column_removed` on a deliberately removed column, then passing after
  the revert. Not "the check passed", which is compatible with a vacuous check.
- **Evidence source for the single inclusion rule**: the Step 9 negative control output — the
  deliberately added second fragment failing the scanner, then passing after removal.
- **Evidence source for the access boundary**: the Step 9 lint negative control output.
- **Residual list**: (a) the device-side migration and bundling path, which no Jest test in this
  item covers — the Step 4 Metro bundle is the only evidence, and the reason it is not a device
  test is quoted from the spec's Out of Scope; (b) the `en` starter labels, which the spec's
  Decision 3 records as provisional and not product-owner reviewed; (c) the five `coming_soon`
  bank identifiers, which the spec's Decision 9 records as provisional.
- **Not deferred, and must not be recorded as residual**: nothing in this item is
  `PENDING HUMAN`. AC24 forbids a device requirement, so every acceptance criterion here is
  agent-verifiable, and the smoke runbook has no human-only step.
